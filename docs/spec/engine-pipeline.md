# Engine pipeline

Resolves [Design the engine pipeline](https://github.com/Ed-Barnes937/FindersEaters/issues/10). Feeds the V0.1 spec (`docs/spec/v0.1.md`), [Design the V0.1 data model](https://github.com/Ed-Barnes937/FindersEaters/issues/13) and [Prototype reviewing and correcting a parsed recipe](https://github.com/Ed-Barnes937/FindersEaters/issues/14).

Every decision here was made by the agent under the owner's standing rules and is reversible: the engine is a pure package behind one seam, its output is regenerable from the original text, and a full re-parse of the library costs fractions of a penny. The one input still owed by the owner is [Run hosted Clef 27B on the held-out golden lines](https://github.com/Ed-Barnes937/FindersEaters/issues/19), which only flips configuration (section 4). The switch from Jev to hosted Clef and the canary that replaces the exact model pin are the owner's decision, recorded in `docs/adr/0002-clef-on-workers-ai.md`.

## 1. Shape in one paragraph

The engine is a pure TypeScript package: `run(input, pins, deps) -> EngineOutput`. `input` is a source document (section 2), `pins` are the recipe's corrections, and `deps` are three ports: a read-only food knowledge base snapshot, a Clef client and the engine configuration. It has no database access (stack ADR). Nine stages run in order. In each stage every decision goes down the same ladder: **pin** (a correction decides it), then **rule** (deterministic code, fail fast), then **Clef** (a typed question over candidates code built), then **review** (a flag for the household). There is no LLM rung in V0.1. Code handles every number; Clef only ever picks from options code supplied. Each decided value carries its source (`correction`, `rule`, `model`, `derived`), and Clef decisions also carry the confidence and the top three alternatives.

## 2. Input: the source document

The engine never fetches. Ingest (capture, server fetch, JSON-LD extraction, manual entry) produces a source document, and that document is the recipe's original text, stored once and never changed:

| Field | Notes |
|---|---|
| `title` | String. |
| `ingredientLines` | Ordered list of raw strings, as captured. A line captured from an HTML section heading carries `heading: true`. |
| `method` | Ordered list of `{ text, heading? }`, like ingredient lines (JSON-LD `HowToStep`s with `HowToSection` names as headings, or the manual-entry text split on blank lines). Not parsed in V0.1. |
| `yield` | Raw string or null ("Serves 4", "Makes 12", "4"). |
| `times` | Raw `prepTime`, `cookTime`, `totalTime` (ISO 8601 durations from JSON-LD; a typed-in total time arrives as `PT<n>M`), each optional. |
| `sourceDomain` | Registrable domain for URL imports (`bbcgoodfood.com`), else null. |

Manual entry has separate title, ingredients, method, servings and time fields, so the engine never splits a pasted blob in V0.1. How each capture route fills this document is the import capture contract, `docs/spec/import-capture.md`.

## 3. The stages

"Gate" is the confidence a Clef answer needs to be accepted without a flag. All gates start at 0.8 (the spike's "always right" line) and live in engine configuration.

| # | Stage | Pin / rule | Clef | Below gate or failure |
|---|---|---|---|---|
| 1 | Normalise | Rule only: decode entities, Unicode NFKC, vulgar fractions to one form, unify dashes and quotes, strip bullets and list numbering, collapse whitespace. Keeps an offset map back to the original line for highlighting. | none | Cannot fail. |
| 2 | Segment | Role: `heading: true`, a trailing colon, or a "For the ..." line is a header; a line starting with a number is an ingredient. Structure: code finds split points ("and", ",", "or", "/"). A correction can pin role and split. | Role Choice (header / ingredient / note) with the next line as context, for lines no rule settles. Structure Choice (single / compound / alternatives) only when code found a split point. Code performs the split. | Top answer applied, flagged. |
| 3 | Classify line kind | No quantity token and a phrase like "to taste", "to serve", "for frying", "for greasing" gives *unquantified*. Tap water and ice (with or without an amount: "500ml boiling water") give *not an ingredient*. | Choice over the three kinds for the rest. | Top answer applied, flagged. |
| 4 | Extract | Code tokenises (splitting "400g" into "400" and "g") and parses every number: integers, decimals, fractions, mixed numbers, ranges ("2-3" stored as min and max) and slashed conversions ("250g/9oz", the second kept as an alternative measure). Arithmetic quantities ("2 cups minus 2 tablespoons") are kept as an expression of two measures and flagged; how they combine belongs to scaling. A note matching "optional" sets the line's `optional` mark. | v2 framing: one Choice per token over quantity, unit, size, ingredient, prep, note (fillers merged in code), plus the ingredient span pick as a cross-check. Code checks Clef's labels: a token labelled quantity must parse as a number, a unit must be in the unit lexicon. | Gate on the lowest token confidence on the line. Top labels applied, flagged. A span pick that disagrees with the token labels, or a failed label check, also flags. |
| 5 | Resolve ingredient | Look the ingredient span up in the knowledge base's name index (own en-gb names, then own other names, then OFF names). One exact hit is `exact`, with no Clef call. No hit and no candidates is `unresolved`, with no Clef call. | Otherwise code builds up to 8 candidates: index hits for sub-spans, longest first, plus each hit's "is a" ancestors (so "a knob of butter" can pick generic butter), plus `none`. Clef picks one. A candidate whose name is the whole span is `exact`, an ancestor or partial-span hit is `parent`, `none` is `unresolved`. | **Unresolved**, with the top candidate offered as a one-tap suggestion. Unknown beats wrong: a wrong ingredient would mislead diet tags and the shopping list. |
| 6 | Resolve unit and unit system | The unit lexicon maps unit words to units (g, kg, ml, l, tsp, tbsp, cup, oz, lb, fl oz, pint, plus count-like units: clove, tin, can, pack, bunch, handful, knob, pinch). "Heaped" and "level" modify the unit. The unit system (UK, US, Australian) is recipe-level: a source-domain table decides it (UK sites and `.co.uk` are UK, `.com.au` and known Australian sites are Australian, known US sites are US). It is only needed when the recipe uses an ambiguous unit (cup, tbsp, pint, oz). | Unknown domain with an ambiguous unit: a Choice over the three systems, with the whole ingredient list as state. | UK (the household default) applied and flagged at recipe level, showing the alternative. This is where the Australian 20 ml tablespoon is handled. |
| 7 | Canonicalise measure | Rule only, from the knowledge base: convert the line's amount to the ingredient's canonical measure through mass, volume, count or pack size conversions, using the unit system. | none | No conversion path: the amount is kept as written and an info flag is raised (the shopping list keeps such amounts apart). Unquantified, not-an-ingredient and unresolved lines skip this stage. |
| 8 | Recipe-level | Title from input. Servings: "Serves N", "N servings" or a bare number is servings; "Makes N ..." is a yield count, recorded as such. Total time: `totalTime`, else `prepTime + cookTime`, else unknown (never inferred from method text). Dietary tags derived from resolved lines and the knowledge base. Protein values gated by the ingredient hierarchy. | Tags as `docs/spec/tag-taxonomy.md` sets out: one Choice per single-valued dimension (with `none`), one Noul per value of a multi-valued dimension, meal-type fallback Choice. Input is title, parsed lines and method text. | Tag below its gate: not applied, offered as a suggestion. Meal-type fallback: applied and flagged. Servings unknown: flagged (scaling needs it). Time unknown: no flag (unknown is a valid fact). |
| 9 | Validate and flag | Rule only: no ingredient lines; a line whose canonical amount is implausible for one recipe (over 5 kg or 5 l, or zero); the same ingredient on two quantified lines in one section; a unit that cannot measure its ingredient (ml of eggs with no conversion); an orphaned correction (section 6). | none | Each finding is a flag. |

No embedding is computed in V0.1: semantic search and similar recipes are out of the cut.

**Not-an-ingredient lines** stay in place in the ingredient list and display as plain text. They never reach the shopping list, scaling or diet derivation. Nothing moves them into the method.

**Optional lines** are marked but still count for dietary derivation, as the taxonomy already says. The mark lets a later "vegetarian if you skip X" read them without a re-parse of the rules.

## 4. Clef: framing, model and stage modes

- **Framing.** V0.1 ships the v2 framing that `run_spike.py --framing v2` sends, with tags taken straight from the taxonomy (`--taxonomy v01`). The request templates move into the engine package unchanged, because the spike showed that even changing the state changes answers. Thresholds are only valid for the exact template they were tuned on.
- **v3, if needed.** Known improvements (generic parents among resolution candidates, the next line as header context, the tap-water rule) are already in the rules and candidate building above, not in the template. Any template change is made on dev lines only, becomes a new framing version, and is adopted only if its held-out result is no worse than v2's on every stage and meets the pass rule in `docs/research/golden-set.md`.
- **Model and provider.** Hosted Clef 27B on Cloudflare Workers AI (`@cf/cloudflare/clef`), per `docs/adr/0002-clef-on-workers-ai.md`. Not Clef-flash or Clef-omni. The base URL and model id come from configuration. Clef takes the same request body as Jev, which the v2 framing was first tuned on, so going back is a configuration change. A model change is a framing change: rerun the golden set first.
- **Canary instead of a pin.** Workers AI has no versioned ids, so the engine cannot name an exact model version. Engine configuration stores the model id plus an **answer fingerprint**: a SHA-256 of the canonicalised answers (choices and probabilities) to the dev golden requests. A CI job sends those requests live once a day and before every release and compares fingerprints. On a mismatch it fails and opens an issue with per-stage scores and the changed answers; production keeps running. Re-baselining the fingerprint is a new engine version, and needs a golden-set rerun under the pass rule first (held-out too, once cleared); a stage that no longer passes goes back to `review-first`, and the cassettes are re-recorded.
- **Confidence.** The engine computes every confidence itself from the returned `probabilities`, with one formula in engine configuration: Jev's normalised form, (p_max - 1/n) / (1 - 1/n), over the n options of the question. It never reads the provider's `confidence` field, which Workers AI fills with a different formula. Gates only mean something under one formula.
- **Stage modes.** Each Clef-backed stage has a mode in configuration:
  - `review-first`: every Clef decision is applied (or left unknown, for resolution and tags) and flagged, whatever its confidence. Rule and pinned decisions are not flagged.
  - `auto`: Clef decisions at or above the gate are accepted silently; below it they follow the "below gate" column.
  V0.1 ships every Clef stage in `review-first`. When the held-out rerun lands, each stage that meets the pass rule flips to `auto`, and an extraction gate of 0.6 is adopted only if held-out accuracy at 0.6 is at least 0.95. Tags flip per dimension (acc@0.8 at least 0.9), as the golden-set doc says.
- **Calls.** One Clef request per ingredient line (all of that line's questions together), plus one for recipe-level questions (unit system and tags). Requests run in parallel, at most 8 at a time. The client keeps connections alive, unwraps the Workers AI envelope (`{result, success, errors, messages}`) and keeps the account ID, which is in the URL, out of logs. Each request has a timeout of about 5 s (hosted Clef measured p50 about 0.5 s, p95 up to 1.4 s from the UK) and up to 2 retries with backoff on rate-limit and transient server errors. At the spike's 3.2k input tokens a line, a 15-line recipe costs about 50k tokens, about 1p at $0.24 per million input tokens.
- **Stored answers.** For every Clef decision the engine output keeps the chosen option, its confidence and the top three alternatives. Review shows the alternatives, and a threshold change can be checked against stored answers before any re-parse.

## 5. Running, failure and review

- **Inline.** Import runs the engine inside the request (stack ADR), with an overall budget of 8 s. The recipe is saved before the engine runs, so nothing the user gave is ever lost.
- **Clef unavailable.** If Clef fails after retries or the budget runs out, the engine finishes every rule-decided part, leaves Clef-dependent decisions unknown (their lines show as original text) and marks the run `partial`. Partial runs are completed lazily on the next read and by the batch re-parse command, as the stack ADR already says. A partial run raises no per-line flags: the recipe shows "still being read" instead.
- **Review never blocks.** A recipe is in the library, searchable and plannable the moment it is saved. Unresolved lines go on the shopping list unmerged, under "other". Unknown tags simply do not match.
- **A flag** has: a target (a line anchor and field, or a recipe-level field), a code (`low_confidence`, `review_first`, `extract_disagreement`, `no_conversion`, `implausible_amount`, `duplicate_ingredient`, `unit_mismatch`, `servings_unknown`, `unit_system_assumed`, `meal_type_fallback`, `tag_suggestion`, `orphaned_correction`, `arithmetic_quantity`), a severity (`check` or `info`), the engine's answer and the alternatives.
- **What review shows** (the contract for the review prototype; the layout is its call): recipe-level flags first (servings, unit system, tag suggestions as one-tap chips such as "Cuisine: Italian?"), then lines in recipe order. Each flagged line shows the original line with the relevant span highlighted, the engine's reading as field chips (amount, unit, ingredient with exact or approximate, prep), up to three one-tap alternatives, and a free edit (the ingredient is picked by autocomplete over knowledge base names and synonyms). Unflagged lines are visible but collapsed. `info` flags are shown but never make a recipe "needs review".
- **Unreviewed** means: the recipe has at least one `check` flag whose target has no correction. That is the library's needs-review boolean. Confirming or correcting a target clears its flag.

## 6. Corrections

- **A correction is an input, not an overlay.** It is a pin: when the engine runs, a pinned decision skips its ladder and every later stage consumes the pinned value. Correcting a line's ingredient therefore recomputes its canonical measure, the recipe's dietary tags and protein gating straight away. The rerun after a correction covers only the deterministic stages (5's consequences, 7, 8's derived parts, 9). Clef is not called again until the next re-parse.
- **Confirming counts.** Accepting the engine's answer in review stores a correction with that same value. It pins the answer against future engine changes and marks the line as a golden-set candidate.
- **Anchors.** The original text never changes, so a line correction is keyed by the original line's index, a part index (0 for a line that was not split) and the field, plus a hash of the original line text as a guard. Recipe-level corrections are keyed by field (servings, total time, title, unit system, or a tag value added or removed).
- **Structural corrections** pin a line's role and its split into parts. A field correction on a part survives a re-parse only while that line still splits into the same number of parts (a pinned split always does). Otherwise it becomes an **orphaned correction**: kept, not applied, and flagged on that line with its old value shown, so nothing the user did is silently lost.
- **Values.** A correction replaces the whole field value (an ingredient id, a quantity with its range, a unit, a kind, a tag added or removed). There are no partial edits. A correction to an ingredient that the knowledge base later retires follows `replaced_by`, as the knowledge base spec says.
- **Effective output** is the engine output computed with the pins applied. It is what search, the planner and the shopping list read. Corrections stay stored separately as the record of what the household decided.

## 7. Versions and re-parse

- **Engine version** identifies everything that can change engine output except the knowledge base: the package version plus a hash of its configuration (rules and lexicons, framing templates, model id and answer fingerprint, confidence formula, gates, stage modes, taxonomy version). Any change to any of these is a new engine version.
- **Each recipe records** its engine version, its KB version, its run status (`complete` or `partial`) and when it ran.
- **A stale engine version** triggers a full re-parse (all nine stages, pins applied), lazily on read and by the batch command. **A stale KB version** alone triggers the partial re-resolution the knowledge base spec defines (stage 5 onwards, no re-splitting). Full re-parse is cheap enough that nothing finer is worth having.
- **Only the current output is stored.** Earlier outputs are not kept: the original text, corrections and the engine version in git are enough to regenerate any of them.
- **The batch re-parse command** prints a diff report per recipe (fields changed, flags added and cleared) before writing, and has a dry-run mode, mirroring the knowledge base build.
- **Gate for a new engine version:** the golden-set suite runs in CI against recorded Clef answers (no live calls) for rule changes, and live on held-out for framing, model, fingerprint or gate changes. A version that drops below the pass rule does not ship.

## 8. No LLM in V0.1

No V0.1 stage needs one: the spike found none, and the messy leftovers it was kept for come from cookbook scanning, which is out of the cut. Whatever the rules and Clef cannot settle goes to review. The ladder's port is shaped so an LLM rung can sit after Clef later (server side only, behind the same interface) without changing any stage.

## Hand-offs

- **[Design the V0.1 data model](https://github.com/Ed-Barnes937/FindersEaters/issues/13)**: the source document as the stored original text; engine output with per-decision source, confidence and alternatives; flags with code, severity and target; corrections keyed by (line index, part index, field, line hash) or recipe field, including confirmations and orphaned state; engine version, KB version, run status and run time per recipe; the needs-review boolean derived from `check` flags without corrections; the `optional` line mark; yield kind (serves or makes).
- **[Prototype reviewing and correcting a parsed recipe](https://github.com/Ed-Barnes937/FindersEaters/issues/14)**: build from section 5's review contract and the flag codes; under `review-first` most Clef-decided lines are flagged, so the prototype must make confirming many lines fast (a "looks right" per line, and one for all unflagged-by-rule lines in a section is worth testing).
- **[Run hosted Clef 27B on the held-out golden lines](https://github.com/Ed-Barnes937/FindersEaters/issues/19)**: its result sets each stage's mode and the extraction gate, nothing else.
- **[Define shopping list merge and regeneration rules](https://github.com/Ed-Barnes937/FindersEaters/issues/23)**: unquantified, not-an-ingredient, optional, unresolved and no-conversion lines as defined here; carbs from "serve with" appear as unquantified lines when the recipe lists them, and otherwise only as a `carb` tag.
- **Scaling (map fog)**: arithmetic quantities arrive as a two-measure expression; ranges as min and max; yield kind tells servings from counts.
- **Display of units (map fog)**: the recipe's unit system is a recipe-level fact with a source-domain rule, so the Australian tablespoon is handled at parse time.
- **Specify the import capture contract** (proposed new ticket): each route must produce the source document in section 2, including `heading` markers from HTML ingredient blocks and the source domain.
