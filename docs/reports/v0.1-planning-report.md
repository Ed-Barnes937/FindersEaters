## 1. Summary

V0.1 is a private, mobile-first web app (a PWA) for one household of two adults. You bring in recipes by pasting a link, sharing from Android, using an iPhone Shortcut, or typing them in. The engine reads each recipe into structured lines and tags, using Jev for the judgement calls and code for every number, with no LLM. Anything the engine is unsure of is left as unknown and shown for a quick check, rather than guessed. You can search the library with filters, build a plan from recipes you pick plus suggestions that each say why they were chosen, and shop from a merged, aisle-sorted list that works offline. It runs on one scale-to-zero Fly machine with Neon Postgres for about £1.75 a month. Accounts are created from a command line; there is no public sign-up.

## 2. Decisions worth your eyes

These are the ones that are most consequential, hardest to reverse, or that depart from `docs/ideation/`.

### 2.1 The engine ships in "review-first" mode, with no LLM

- **Choice:** Jev v2 prompts ship unchanged with the model pinned. Every Jev stage asks you to confirm its answer until your held-out rerun proves it accurate; then config flips stages to automatic (gate 0.8). No LLM is called anywhere in V0.1.
- **Rejected:** auto-accepting Jev answers at confidence 0.8 from day one, based on the phase 2 spike.
- **Why:** the spike tested on lines that also shaped the prompts. Fresh-line accuracy is unknown. Review costs about 7 taps for a 17-line recipe, which the review prototype judged acceptable.
- **Look at:** the golden-set labels are the agents' judgement, not yours. Some are contestable (stroganoff as central_eastern_european, pancakes as a British dessert, leek and potato soup as british, naan's method as fry).
- **Ticket:** [Design the engine pipeline](https://github.com/Ed-Barnes937/FindersEaters/issues/10), [Build a golden set from the household's own recipes](https://github.com/Ed-Barnes937/FindersEaters/issues/4)

### 2.2 "Unknown beats wrong" everywhere

- **Choice:** an ingredient, tag or unit below its confidence gate is stored as unknown, with a one-tap suggestion. Diet tags are only derived from ingredients, never read from site labels. Households cannot create their own ingredients; a line resolves exactly, to a parent, or not at all.
- **Rejected:** best-guess answers that the user corrects later.
- **Why:** a wrong "vegetarian" tag or a wrong ingredient silently corrupts search, suggestions and shopping. An unknown is visible.
- **Look at:** about a third of golden-set ingredients are not fully covered by open data, so the hand-written "own layer" of the knowledge base matters. The plan is that you review every golden-set ingredient in it. That is real work for you before go-live.
- **Ticket:** [Design the tag taxonomy](https://github.com/Ed-Barnes937/FindersEaters/issues/7), [Decide how the food knowledge base is seeded](https://github.com/Ed-Barnes937/FindersEaters/issues/9), [Check seed-source coverage of golden set ingredients](https://github.com/Ed-Barnes937/FindersEaters/issues/8)

### 2.3 Only the iPhone captures pages on the device

- **Choice:** the iPhone Shortcut sends a trimmed copy of the page from Safari. Paste a link and Android share send only the URL, and the server fetches the page once. There is no headless browser or fetch proxy. If the fetch fails, the app offers "Type it in" with the link prefilled.
- **Rejected:** a headless browser or fetch proxy on the server.
- **Why:** cost and simplicity, and a desktop or Android bookmarklet is the planned fix for blocked sites.
- **Departs from ideation:** the README says import captures on the device because several UK sites block server fetches, with server fetch as the fallback. For Android and paste, server fetch is now the only route. Whether the Fly London IP gets blocked is unmeasured; the spec says to measure it during the build.
- **Ticket:** [Specify the import capture contract](https://github.com/Ed-Barnes937/FindersEaters/issues/24), [Prototype the iPhone Shortcut against a stub import endpoint](https://github.com/Ed-Barnes937/FindersEaters/issues/27)

### 2.4 The shopping list is computed, never stored

- **Choice:** the list is worked out on every read from the plan and the recipes. Only ticks are stored, in one `shopping_tick` table, each with a snapshot of the amount bought. A plan's list covers every item in the plan, whatever its date. Ticks reset only when you start a new plan by hand; uncooked items and their ticks carry over and show as "Bought for last plan".
- **Rejected:** stored list rows that are regenerated, and a list per week or per date range.
- **Why:** nothing to keep in sync, and "you bought 200 g, you now need 300 g" falls out of the snapshot.
- **Look at:** the tick mutation's input is a frozen contract, because offline ticks can replay days later. A long-running plan with no end date keeps its ticks until you press New plan.
- **Ticket:** [Define shopping list merge and regeneration rules](https://github.com/Ed-Barnes937/FindersEaters/issues/23), [Define the plan lifecycle and what a shopping list covers](https://github.com/Ed-Barnes937/FindersEaters/issues/26)

### 2.5 A plan item is one recipe, and there is no "one meal a day" setting

- **Choice:** a plan is a list of single recipes, each with its own servings and an optional date. Any number can share a date. There is no meal entity or meal slot. Meal type and count are parameters of a suggestion request; the UI defaults to dinner, one a day.
- **Rejected:** a plan item as a meal of several recipes (curry, rice and a side), and a stored household "what we plan" setting.
- **Why:** simplest model, and meal grouping can be added later as an optional field without a migration.
- **Departs from ideation:** the README said a household setting ("1 hot meal a day") sets the defaults. That setting is out. Sides are suggested only when you ask for them.
- **Ticket:** [Decide whether a plan item is one recipe or a meal](https://github.com/Ed-Barnes937/FindersEaters/issues/3), [Agree the V0.1 feature cut](https://github.com/Ed-Barnes937/FindersEaters/issues/2)

### 2.6 Suggestions use a flat "recently cooked" penalty, not cadence

- **Choice:** five fixed-weight terms: ingredient overlap (+1.0), favourite (+0.6), effort (+0.3), recently cooked (-0.5, fading over 28 days for every recipe) and variety (-1.0). Each term is a reason shown in words, never as a number. No presets.
- **Rejected:** learned per-recipe cadence and presets like "Easy week".
- **Why:** cadence needs plan history that does not exist yet. A single 28-day gap is the simple case of cadence and can be replaced later.
- **Departs from ideation:** the README's "cadence, not recency" principle is deferred. A loved but expensive meal will come round as often as any other after 28 days.
- **Ticket:** [Design suggestion scoring and selection](https://github.com/Ed-Barnes937/FindersEaters/issues/12), [Prototype building a plan with suggestions](https://github.com/Ed-Barnes937/FindersEaters/issues/15)

### 2.7 Stack: own repo, Neon, no job queue

- **Choice:** a standalone repo copying HomeOfEd's stack (not inside the HomeOfEd monorepo). Neon Postgres, not Fly Postgres. Engine work runs inside the request that needs it, finished lazily if interrupted. One scale-to-zero Fly machine.
- **Rejected:** living inside HomeOfEd and sharing its packages; a Postgres-backed job queue; Fly Managed Postgres ($38+ a month).
- **Why:** this is a product with its own release path; scale-to-zero cannot see background jobs, and an always-on worker costs more than the whole app.
- **Look at:** this is the only decision with an ADR (`docs/adr/0001-stack-and-hosting.md`). Bulk imports (link packs) will need a real queue before V1.
- **Ticket:** [Choose the stack and hosting](https://github.com/Ed-Barnes937/FindersEaters/issues/6), [Research the cheapest viable fly.io setup](https://github.com/Ed-Barnes937/FindersEaters/issues/5)

### 2.8 Email and password only, accounts by CLI, on a temporary domain

- **Choice:** Better Auth with email and password. No public sign-up. A CLI creates the household and both users, and resets passwords. 90-day sliding sessions. The app lives on a `homeofed.com` subdomain for V0.1.
- **Rejected:** magic links and OAuth, because the link opens in Safari, whose storage is separate from the installed iPhone app, so you would sign in to the wrong place.
- **Why:** it works in the iOS Home Screen app with no email vendor.
- **Look at:** moving to a product domain later means reinstalling the app on every phone, and passkeys wait for that move. There is no in-app password reset.
- **Ticket:** [Decide auth, sign-in and import tokens](https://github.com/Ed-Barnes937/FindersEaters/issues/20)

### 2.9 Staging holds your real data

- **Choice:** before every release, staging is refreshed by restoring the latest production backup. Nightly `pg_dump` backups go to Tigris and are restored and checked each night. Dumps are not encrypted on the client side.
- **Rejected:** synthetic or anonymised staging data.
- **Why:** it tests the backup and the migrations on real data every release, and only one household exists.
- **Look at:** this must change before a second household exists.
- **Ticket:** [Define deploy, migration and backup operations](https://github.com/Ed-Barnes937/FindersEaters/issues/21)

### 2.10 Two score-4 features were cut or shrunk

- **Similar recipes** (scored 4 in `features.md`) is out. The reason given: a browsing nicety for a 50 to 150 recipe library, and the planner's overlap scoring proves the same machinery.
- **Preferred units and locale** (scored 4) is reduced to one fixed value, `uk_metric`, with no UI. US and AU measures are still parsed; non-metric lines show a metric hint.
- These break the "score 4-5 is in" rule. The feature cut ticket says you agreed them.
- **Ticket:** [Agree the V0.1 feature cut](https://github.com/Ed-Barnes937/FindersEaters/issues/2)

## 3. All decisions by area

### Product scope

- [Agree the V0.1 feature cut](https://github.com/Ed-Barnes937/FindersEaters/issues/2): score 4-5 in, 3 out, foundations (⚑) designed for but not built. Also in: ingredient hierarchy at seed depth, provenance, crude aisle grouping, offline shopping list only, skip-only suggestions.
- [Decide whether a plan item is one recipe or a meal](https://github.com/Ed-Barnes937/FindersEaters/issues/3): one recipe per item, optional date, no meal slots.
- [Assemble the V0.1 spec](https://github.com/Ed-Barnes937/FindersEaters/issues/18): `docs/spec/v0.1.md` with 29 user stories, module seams, a table of where later decisions overrode earlier specs, a 10-milestone build order and acceptance criteria.
- Same ticket also closed: units display (`uk_metric`, kg/l step-up, metric hints), a daily Jev cap of 2,000 requests, a 20-second list refetch instead of live push, and optional lines counting for diet and shopping.

### Data model

- [Design the V0.1 data model](https://github.com/Ed-Barnes937/FindersEaters/issues/13): durable data (original text, corrections, plans, ticks) is relational. Engine output is one JSON document per recipe plus rebuildable search tables. Recipes are soft-deleted. UUIDv7 ids. One household per user.
- A dated plan item counts as a cooking. There is no "cooked" button; last cooked and times cooked are derived.
- Every foundation (members, sub-recipes, rules, cadence and so on) has a named, additive landing spot.

### Engine

- [Design the engine pipeline](https://github.com/Ed-Barnes937/FindersEaters/issues/10): each decision goes correction, then rule, then Jev, then a review flag. Code does all numbers. Corrections are pins that survive re-parse; orphaned ones are flagged, never dropped.
- Unit system (UK, US, AU) is a recipe-level fact from a table of source domains. Engine version changes trigger a full re-parse.
- [Design the tag taxonomy](https://github.com/Ed-Barnes937/FindersEaters/issues/7): 8 fixed dimensions (meal, cuisine, protein, carb, method, effort, equipment, diet). Time is a number, not a tag. Season is dropped. User tags are for search only.
- [Build a golden set from the household's own recipes](https://github.com/Ed-Barnes937/FindersEaters/issues/4): one `golden.json` split into a dev set for tuning and a held-out set for reporting. CI runs it against recorded Jev answers.
- [Decide how the food knowledge base is seeded](https://github.com/Ed-Barnes937/FindersEaters/issues/9): built from pinned Open Food Facts, Intake24 and USDA data plus our own reviewed YAML. Every fact has a source. Own layer wins.
- [Check seed-source coverage of golden set ingredients](https://github.com/Ed-Barnes937/FindersEaters/issues/8): Open Food Facts resolves 76% of golden ingredients; 66% are fully covered. The own layer owns allergens and aisles.

### Review and correct

- [Prototype reviewing and correcting a parsed recipe](https://github.com/Ed-Barnes937/FindersEaters/issues/14): one list in recipe order. Uncertain lines are cards with up to 3 one-tap answers. "Looks right - confirm N" covers the rest. Review never blocks using the recipe, but needs a connection.

### Search and library

- [Define the query model](https://github.com/Ed-Barnes937/FindersEaters/issues/11): one and/or/not query tree over registered fields, compiled to one SQL query. Unknown never matches a filter. Rules (later) are a query plus a min or max.
- [Specify the search and library screens](https://github.com/Ed-Barnes937/FindersEaters/issues/22): library and search are one Recipes screen. Typing a word suggests filters (no natural-language search). Text-only rows, no images. Default sort is recently added.

### Planning and suggestions

- [Design suggestion scoring and selection](https://github.com/Ed-Barnes937/FindersEaters/issues/12): hard filter, then five scored terms. Picks are deterministic and avoid three of the same protein, carb or cuisine. Suggestions are never stored.
- [Prototype building a plan with suggestions](https://github.com/Ed-Barnes937/FindersEaters/issues/15): suggestions appear inline as dashed cards. Each shows up to two reasons, a "Why this?" view, and Add, Another and Swap.
- [Define the plan lifecycle and what a shopping list covers](https://github.com/Ed-Barnes937/FindersEaters/issues/26): you start a new plan by hand, prompted by a banner when the old one is finished. Uncooked items move across. Past plans stay editable.
- [Define recipe scaling rules](https://github.com/Ed-Barnes937/FindersEaters/issues/25): one shared scaling function for the recipe view and the list. Scale by servings only, no separate multiplier. Notes flag eggs, part packs and seasoning that do not scale cleanly.

### Shopping

- [Define shopping list merge and regeneration rules](https://github.com/Ed-Barnes937/FindersEaters/issues/23): one row per ingredient, no merging up the hierarchy. Always-haves cover the ingredient, its kinds and its parents. A fixed 9-aisle walk order. "Serve with rice" adds rice as an unquantified row.
- [Prototype the shopping list in the shop](https://github.com/Ed-Barnes937/FindersEaters/issues/16): tap a row to tick it, with 4-second undo; ticked rows move to "In the basket". Ticks queue offline and replay; the later device tick wins.

### Import

- [Specify the import capture contract](https://github.com/Ed-Barnes937/FindersEaters/issues/24): every route sends one "capture" to one server-side extractor (JSON-LD first, then microdata). Duplicates match on the canonical URL. The raw capture is kept as evidence.
- [Prototype the iPhone Shortcut against a stub import endpoint](https://github.com/Ed-Barnes937/FindersEaters/issues/27): the Shortcut runs a small script that keeps only the recipe parts of a page, cutting size by 45-70%. Every failure has a defined message. Build sheet in `docs/spec/ios-shortcut.md`.

### Auth

- [Decide auth, sign-in and import tokens](https://github.com/Ed-Barnes937/FindersEaters/issues/20): email and password, CLI-created accounts, 90-day sessions. Each iPhone gets its own import token, shown once, revocable, with no expiry, limited to 30 imports an hour.

### Stack and ops

- [Research the cheapest viable fly.io setup](https://github.com/Ed-Barnes937/FindersEaters/issues/5): one scale-to-zero Fly machine in London plus Neon, about £1.75 a month.
- [Choose the stack and hosting](https://github.com/Ed-Barnes937/FindersEaters/issues/6): pnpm and Turborepo, Fastify and tRPC, Drizzle, React with Vite and TanStack, Base UI. Production from `main`, staging from `develop`.
- [Define deploy, migration and backup operations](https://github.com/Ed-Barnes937/FindersEaters/issues/21): migrations only add in a release and remove in a later one, enforced by CI. Fix forward; rollback is the previous image. Nightly verified backups.
- Testing (from [Assemble the V0.1 spec](https://github.com/Ed-Barnes937/FindersEaters/issues/18)): zero test retries, one Postgres container per run, Playwright end to end at phone width including offline ticking.

### Design

- [Write the Claude Design brief](https://github.com/Ed-Barnes937/FindersEaters/issues/17): a self-contained brief at `docs/spec/design-brief.md` covering three moments of use (sofa, shop, just found a recipe), every screen at 390 px, and a calm, plain tone.
- Agents also decided the Settings screen, the paste-friendly manual entry form, and read-only lists for past plans. Prototype colours and fonts are not locked.

## 4. Waiting on you

Neither of these blocks building. Both only change configuration or a few numbers.

### Rerun Jev v2 on the held-out golden lines

- **What it is:** [Rerun Jev v2 on the held-out golden lines](https://github.com/Ed-Barnes937/FindersEaters/issues/19).
- **What it needs:** your `JEV_API_KEY`. First, spot-check the agents' labels on 136 extraction lines and 65 resolution lines, and optionally add more of your own recipes. Then run `python3 run_spike.py --framing v2 --set heldout` in `docs/ideation/research/jev-spike`, and record accuracy per stage and per tag dimension.
- **Why it does not block:** V0.1 ships with every Jev stage review-first. The result only flips config: which stages become automatic, whether the extraction gate can drop to 0.6, and which tag dimensions auto-apply. Until then you confirm more answers by hand.

### Run the iPhone Shortcut device checks

- **What it is:** [Run the iPhone Shortcut device checks](https://github.com/Ed-Barnes937/FindersEaters/issues/28).
- **What it needs:** a current iPhone and about 30 minutes. Run the 11-step protocol on branch `prototype/ios-shortcut` (a stub server plus a cloudflared tunnel). Record whether large bodies get through, when iOS asks about large data, whether error messages show, the request timeout, and the first-run prompts.
- **Why it does not block:** the Shortcut was redesigned so every risky iOS behaviour has a defined fallback. The results only set the size cap (CAP, now 1M characters), one how-to step, and maybe a lower engine time budget for the iPhone route. That route is milestone 9 of 10.

## 5. Remaining fog and out of scope

### Not yet specified (none blocks V0.1)

- **Before a public V1:** a product domain, a bulk import queue, the ODbL licence question for the knowledge base, an email vendor for password reset and invites, passkeys, anonymised staging data.
- **Engine and food data:** UK 14 allergens, prep-specific densities, whether bulk-confirmed answers should give way to a better engine answer later.
- **Suggestions:** pack-aware overlap, weekday vs weekend effort, variety over plans of two weeks or more, a cost signal, overlap tuning for small libraries (checked by the planner evaluation before go-live).
- **Import:** whether servers block fetches from Fly's IP, a bookmarklet for desktop and Android, re-importing from a stored capture, the Shortcut timeout.
- **Other:** recipe images, iOS session persistence, backup encryption, promoting staging's image to production, scaling notes from method text (oven times, tin sizes), a "clear ticks" control, the final visual identity.

### Out of scope

Household sharing UX and invites, cookbook scanning, link packs, cookbook barcode import, the Capacitor app and iOS share extension, household members, similar recipes, search beyond filters (natural language, semantic, saved collections), planner extras (dismiss with a reason, leftovers, presets, learned cadence), active vs waiting time, round to buyable amounts, location selection, rating and notes UI, meal pairing, and free-text shopping items like "bin bags".
